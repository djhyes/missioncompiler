# MissionCompiler V0.1 产品需求文档

状态：POC 基线
日期：2026-08-24
产品定位：AI 任务编译器
首个执行引擎：Codex
首个平台：macOS

## 1. 产品摘要

MissionCompiler 让不熟悉 Agent 技巧的用户只描述目标，系统负责检查环境、澄清意图、选择执行模式与能力、解释权限和风险、生成验收条件，并在用户批准后驱动 Codex 完成和验证任务。

一句话价值：

> 用户批准目标、影响和风险；MissionCompiler 处理模型、模式、Skills、插件、MCP、执行与验收。

V0.1 不试图支持所有 Agent 和所有办公任务。它专门帮助不会编程或不想学习 Agent 配置的创业者、产品经理和小团队负责人，更安全、更高成功率地让 Codex 完成本地代码任务。

## 2. 问题

普通用户面对的不是一个提示词问题，而是一组相互依赖的决策：

- 该直接执行还是先计划。
- 当前可用模型中哪个适合，推理强度多高。
- 是否需要 Skill、插件、MCP 或外部连接。
- 安装来源是否可信，需要哪些权限。
- 应在当前目录、快照还是独立 worktree 中执行。
- 哪些动作可以一次批准，哪些必须逐次批准。
- Agent 说“完成”后，怎样证明真的完成。

现有产品通常把这些选项暴露给用户，或让模型在执行中临场判断。前者增加学习成本，后者缺少一致、可审计的安全边界。

## 3. 产品原则

1. **先事实，后建议。** 能从仓库、配置、日志或工具状态查到的信息不问用户。
2. **先合同，后执行。** 修改前生成结构化 TaskSpec 和人类可读方案卡。
3. **动态发现。** 不写死模型、reasoning effort、Skills、插件和 MCP 清单。
4. **最小能力。** 没有任务需要就不加载、不连接、不安装。
5. **风险不可被模型信心覆盖。** 红色外部动作逐次批准；违反约束直接阻塞。
6. **完成必须有证据。** 测试、检查、Reviewer 和验收条件优先于 Agent 自述。
7. **本地优先。** 默认不上传源码；配置和凭据留在本机安全边界内。
8. **失败可恢复。** 修改前决定工作区策略、停止条件和回滚方法。

## 4. 目标用户

### 主要用户

- 正在用 Codex 修改代码、但不会编程的创业者。
- 能定义业务目标和验收结果、但不想管理 Agent 设置的产品经理。
- 缺少专职工程团队的独立开发者和小公司负责人。

### 暂不服务

- 需要完全无人值守生产运维的企业。
- 需要自动付款、真实交易或监管提交的流程。
- 同时编排多个模型供应商和大量 Agent 的复杂组织。
- 需要云端托管源码的团队。

## 5. 用户任务

用户的核心 Job to Be Done：

> 当我想让 AI 完成一个代码任务时，我只想说清楚目标和不可触碰的边界，让系统检查真实环境、提出一套可信方案，并在我理解影响后把任务做完、验证好、可撤销地交付。

V0.1 支持六类入口，其中前五类可执行：

1. 修复 Bug。
2. 增加小功能。
3. 代码 Review。
4. 修复测试。
5. 项目安装和配置。
6. 只读分析，用于路由和体验完整性。

## 6. 范围

### V0.1 必须提供

- 中文和英文原始需求输入。
- 只读环境扫描。
- TaskSpec 生成。
- Plan / Direct 推荐。
- 模型层级和 reasoning effort 推荐，并在运行时映射真实可用模型。
- Skills、插件和 MCP 的按需推荐与信任说明。
- 权限与风险分级。
- 一张可读的执行方案卡。
- 用户批准、修改或取消。
- Git worktree / 当前工作区 / 非 Git 快照策略。
- Codex 执行、测试、有限修复循环和 Review。
- 最终报告与回滚方法。
- 30 个初始评测任务和可重复规则回归测试。

### V0.1 明确不做

- 自动生产部署。
- 自动发送邮件或消息。
- 自动付款、购买或真实订单。
- 自动监管、法律或财务提交。
- 未知来源能力的自动安装。
- 云端源码托管。
- 多供应商通用 Agent 编排。
- 无限自主循环。
- 自动把一次成功流程写入用户全局 Skill 目录。

## 7. 端到端体验

### 7.1 输入

首页只有一个主要输入：

> 你想完成什么？

用户可以补充不可改变项，例如“必须保持 dry-run”“不能发布”“不要碰现有未提交代码”。高级设置默认收起。

### 7.2 只读扫描

系统在不修改状态的前提下检查：

- 当前目录、仓库和 Git 状态。
- 项目说明、AGENTS.md、README、docs、scripts。
- 技术栈、构建、测试和静态检查命令。
- 用户未提交改动。
- 当前可用模型与推理等级。
- 可用 Skills、插件、MCP 及认证状态。
- 有效权限和管理员要求。
- 需求中能从源码确认的事实。

扫描结果必须标记来源和时间；失败项显示为未知，不能用猜测填充。

### 7.3 编译

系统生成 TaskSpec，并通过确定性策略计算：

- 风险等级。
- Plan / Direct。
- 模型层级和推理强度。
- 工作区策略。
- Reviewer 要求。
- 审批时机和停止条件。

### 7.4 执行方案卡

普通模式只显示：

- 系统理解的目标。
- 将交付什么。
- 推荐执行方式。
- 将读写哪些范围。
- 需要哪些能力及原因。
- 风险和审批点。
- 验收条件。
- 回滚方法。

主要操作：

1. 按推荐方案执行。
2. 修改方案。
3. 取消。

模型名、reasoning effort、原始工具日志等放在“技术细节”中，不要求普通用户理解。

### 7.5 准备与执行

用户批准后：

1. 再次核对批准范围与当前环境是否漂移。
2. 建立 worktree 或快照。
3. 仅加载已批准能力。
4. 执行计划。
5. 运行验证。
6. 在明确上限内自动修复普通失败。
7. Reviewer 对照 TaskSpec 检查。
8. 通过后生成报告；否则停止并解释缺口。

任何新增红色动作都在发生前弹出独立批准，不沿用方案卡的一次批准。

### 7.6 最终报告

报告必须回答：

- 做了什么。
- 哪些文件或外部对象发生变化。
- 每个验收条件是否通过，证据是什么。
- 哪些测试和检查运行过。
- 是否出现未完成项或剩余风险。
- 如何回滚。

## 8. 状态模型

```text
DRAFT
  → SCANNING
  → PROPOSAL_READY
  → AWAITING_APPROVAL
  → PREPARING
  → EXECUTING
  → VERIFYING
  → COMPLETED
```

旁路状态：

- `NEEDS_INPUT`：只有不可从环境发现的必要选择。
- `NEEDS_ACTION_APPROVAL`：即将执行红色动作。
- `BLOCKED`：违反约束或无法建立信任。
- `FAILED_VERIFICATION`：有界修复后仍不通过。
- `CANCELLED`：用户取消。
- `ROLLED_BACK`：已执行回滚。

环境事实、批准范围或用户目标变化时，回到 `SCANNING` 或 `PROPOSAL_READY`，不能沿用过期批准。

## 9. 功能需求

### FR-01 原始需求输入

- 保留用户原始文本。
- 支持明确禁止项和不可变条件。
- 不强迫用户填写技术字段。

验收：同一 TaskSpec 能追溯原始需求，且禁止项没有在优化中丢失。

### FR-02 环境扫描

- 默认只读。
- 识别项目文档、技术栈、命令、Git 和能力目录。
- 区分已观察、用户声明和推断。

验收：扫描失败不会修改文件，也不会把未知标成已确认。

### FR-03 TaskSpec 编译

- 输出符合 JSON Schema 的对象。
- 至少包含目标、交付物、禁止项、验收、事实、推荐、审批、验证和回滚。

验收：Schema 校验通过，每个 required 验收项都有验证方法。

### FR-04 策略决策

- 使用可版本化、可回归测试的确定性规则。
- 模型不能修改红色动作或阻塞条件的含义。

验收：30 个基线评测任务全部匹配预期政策。

### FR-05 能力解析

- 动态读取当前可用能力。
- 根据任务语义、技术栈、信任、权限和必要性排序。
- 缺少能力时优先可信来源或无新增能力方案。

验收：本地小修改不会无理由推荐外部 MCP；未知来源能力被阻塞。

### FR-06 方案卡

- 普通视图不暴露不必要术语。
- 显示影响范围、风险、验收和回滚。
- 技术细节可展开。

验收：用户无需理解具体模型或 MCP 也能判断是否批准。

### FR-07 审批

- 黄色操作支持方案卡一次批准。
- 红色动作逐次批准。
- 批准带作用域和有效期。

验收：旧批准不能覆盖新增路径、权限或外部动作。

### FR-08 工作区保护

- 检测未提交改动。
- 多文件、复杂或脏工作区任务优先 worktree。
- 非 Git 项目修改前创建可恢复快照。

验收：用户原有改动不被覆盖、清理或自动提交。

### FR-09 执行

- 将 TaskSpec 编译为 Codex 任务。
- 限制工具、权限、目录和停止条件。
- 自动修复循环有次数或时间上限。

验收：执行不能越过批准范围；达到上限后停止并报告。

### FR-10 验证与 Review

- 执行项目已有测试、构建和静态检查。
- 视觉任务需要真实浏览器检查。
- 修改任务、能力安装或红色任务需要 Reviewer。

验收：完成状态由证据计算，不由模型自由宣告。

### FR-11 回滚

- 执行前确定回滚策略。
- 文件变更优先丢弃隔离 worktree 或恢复快照。
- 外部动作说明人工撤销路径。

验收：每个完成或失败任务都有明确回滚入口或说明无需回滚。

### FR-12 结果记录

- 本地记录任务类型、环境摘要、推荐、用户修改、执行结果、成本和人工介入。
- 默认不保存源码全文、秘密或原始外部联系人数据。

验收：记录足以评估路由质量，但不包含不必要敏感内容。

## 10. 风险与权限

| 等级 | 示例 | 默认行为 |
|---|---|---|
| 绿色 | 读项目、搜索、分析本地测试 | 自动只读执行 |
| 黄色 | 修改 workspace、限定网络、可信能力安装 | 方案卡一次批准 |
| 红色 | 发送、发布、生产、付款、真实订单、监管提交 | 每次动作前批准 |
| 阻塞 | 违反禁止项、未知来源能力 | 不执行，必须换方案 |

敏感数据原则：

- 不主动读取密钥值；优先检查“是否已配置”。
- 凭据交给 macOS Keychain 或现有认证机制。
- 日志和 TaskSpec 对秘密做脱敏。
- 云端统计默认不含源码和原始提示词。

## 11. 技术架构

### 正式 V0.1

```text
SwiftUI macOS Client
  ├── Environment Scanner
  ├── Intent Compiler
  ├── Deterministic Policy Core
  ├── Capability Resolver
  ├── Approval Controller
  ├── Codex Adapter
  │     ├── App Server：深度会话、模型/能力/权限发现、审批与流式事件
  │     ├── SDK / exec：自动化执行
  │     └── Stable CLI：MCP、插件与诊断的稳定命令入口
  ├── Verifier / Reviewer
  └── Local Store
        ├── SQLite：任务、决策、结果
        └── Keychain：凭据
```

平台适配层以 TaskSpec 为边界。未来接入 Claude Code 或其他 Agent 时，只新增 Adapter，不改变核心风险合同。

### 当前 POC

- Repo-scoped Codex Skill：环境扫描、意图编译与方案卡。
- Python 标准库规则引擎：确定性风险与路由。
- JSON Schema：TaskSpec 合同。
- 30 个 JSON 评测任务：策略回归。
- HTML 交互原型：验证普通用户流程。

## 12. 当前 Codex 集成边界

依据 2026-08-24 官方文档：

- App Server 适合深度产品集成，提供会话、审批和流式 Agent 事件。
- `model/list` 可动态返回模型、默认值和支持的推理等级。
- `skills/list`、`permissionProfile/list`、`collaborationMode/list`、`mcpServerStatus/list` 和 `config/read` 可建立真实环境快照。
- App Server 的 `plugin/list`、`plugin/read`、`plugin/install`、`plugin/uninstall` 仍标为 under development，官方明确不建议生产客户端调用。
- 本地 Skill 可放在仓库 `.agents/skills`，Codex 支持显式或基于描述的隐式激活。
- MCP 可通过稳定 CLI 管理，并支持工具级审批策略。

因此：正式客户端可以用 App Server 做发现和会话，但第一版插件安装/管理必须通过稳定用户界面或 CLI Adapter，并保留人工审批和版本固定。

## 13. 非功能需求

### 安全

- 默认最小权限和 fail closed。
- 无批准的红色动作数量必须为 0。
- 所有能力安装显示来源、版本和权限。

### 隐私

- 默认本地处理源码。
- 远端调用前显示数据边界。
- 统计只保存完成评估所需的最小字段。

### 可靠性

- 环境事实带时间和来源。
- 方案与执行之间检测漂移。
- 每个规则变更必须运行评测集。

### 可解释性

- 每个推荐给出 1–3 条直接理由。
- 用户可以展开规则事实和技术细节。
- 不用含糊的“AI 认为更好”作为理由。

### 性能

- 本地扫描目标：普通项目 10 秒内完成基础结果。
- 方案卡目标：扫描完成后 15 秒内出现首版。
- 不为低风险分类任务默认调用最强模型。

## 14. 成功指标

北极星指标：

> 无未批准副作用的验收通过率。

POC 指标：

- 30 个政策评测任务通过率：100%。
- 红色动作漏拦截：0。
- 未知来源能力自动安装：0。
- 用户对方案卡“直接批准”的比例。
- 用户修改推荐模式、权限或能力的比例。
- 相比直接输入原始提示词，最终验收通过率的提升。
- 每个成功任务的人工介入次数、耗时和模型成本。

不要用“生成了答案”或“Agent 表示完成”作为成功指标。

## 15. POC 实验

### 实验 A：方案理解

让目标用户对 10 个方案卡回答：系统要做什么、会改什么、有什么风险、如何判断完成。目标是四个问题无需查看技术细节即可正确回答。

### 实验 B：推荐接受度

对 30 个任务记录用户是否接受 Plan / Direct、模型层级、能力和权限建议，以及修改原因。

### 实验 C：完成质量

同一任务比较两种路径：原始提示词直接执行 vs. MissionCompiler 编译后执行。统一以验收条件、测试和 Review 评分。

### 实验 D：能力克制

检查系统是否在无需外部数据的本地任务中错误推荐插件或 MCP。

## 16. 发布门

POC 进入 macOS 工程实现前必须满足：

- PRD、TaskSpec 和策略规则完成评审。
- 30 个任务全部通过确定性回归。
- Skill 结构校验通过，无 TODO 或未定义审批语义。
- 至少 10 个真实仓库任务完成前向试用。
- 没有未批准写入、安装或外部动作。
- 方案卡可被非技术用户正确理解。

正式 V0.1 测试发布前额外要求：

- 工作区保护和回滚经过故障注入。
- App Server / CLI 版本兼容策略完成。
- 插件与 MCP 供应链检查完成。
- 本地数据和 Keychain 威胁模型完成。
- 遥测默认关闭或明确同意。

## 18. 待验证假设

- 用户愿意在执行前花约 30–60 秒查看方案卡。
- 规则＋模型比单独依赖强模型更稳定。
- 用户真正关心的是影响和风险，而非模型名和 Agent 术语。
- 初期无需跨 Agent，也能证明产品价值。
- 成功率与人工介入数据足以形成长期 Router 护城河。

这些是假设，不应在 POC 前当作已验证结论。
